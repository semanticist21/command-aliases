# Harness

Read the target's instructions, docs, code, and git state. Keep only explicit durable decisions or verified non-obvious constraints in one existing owner; user scope holds cross-project facts, project scope only that project. For each requested web, backend, Flutter, or database runtime, trace its roots, shared contracts, and authority boundaries. If that runtime has an established structure, ask whether to preserve or migrate it: preserve means document its verified constraints; migrate requires explicit approval and includes the necessary code, dependency, and folder changes. Otherwise set up only the requested parts of this default profile: web uses React/TypeScript feature slices separating feature route modules, components, API/query, and mappers; ConnectRPC gRPC-Web owns transport, TanStack Query server/cache state, and TanStack Router route composition/navigation. Backend uses Rust/Tonic gRPC, SQLx for PostgreSQL access, feature-first modules, orchestration for cross-feature workflows, shared PostgreSQL, and transactional-outbox workers. Flutter uses feature `api/models/state/components`; GoRouter composes feature route modules into the app route tree; Riverpod owns feature state; generated Dart `grpc` bindings stay behind a shared API boundary. Unless the project establishes another lifecycle, make SQL schema guidance follow this default: before commercial production, domain-ordered SQL shards are an idempotent declarative current-state baseline, edited directly in non-production with no migration history, backfill, or destructive patch mixed in; at commercial cutover, bootstrap production once from the frozen baseline; thereafter, use a separate ordered append-only migration chain for approved durable production schema changes, never rewriting or mixing it into the frozen baseline. If the requested profile conflicts with an intentional existing structure, production data already exists, a platform requires its own migration runner, or SQL is not the primary data model, invoke `$grill-me` and settle the design before documenting or structuring it. Put cross-runtime rules in the root harness and add nearest-scope rules only where they prevent a local architectural drift; do not promote an optional pattern to a global architecture. Setup creates the minimum root harness/compatibility link; add writes a few current-state lines; polish verifies then deletes duplication, history, measurements, walkthroughs, and code-derived facts.

Before deleting dated logs, handoffs, or other history, check the applicable project instructions. If they expressly require retaining them, do not delete them: state the conflict between that policy and this skill's current-state preference, then ask whether to preserve the exception or migrate to the current-state model. Migration requires explicit approval and updates to the governing project instructions. Ask on conflict and verify references/diff.
